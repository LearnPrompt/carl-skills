# 三色：目录一层，条目一层

两层颜色回答两个不同的问题。目录那层回答「这个文件夹现在有多乱，值不值得花时间」，
条目那层回答「这一条我能不能直接勾」。两层各算各的，不互相推导，
也不允许一层的结果去改另一层。

颜色不是文案，是权限。审核页上的按钮直接跟着 `color` 走，所以这个字段永远由规则算出来，
不由谁写上去。规则改了颜色跟着变，措辞改了颜色不变。

## 条目层：`action.color`

| 颜色 | 含义 | 覆盖哪些动作 | 页面给什么按钮 |
|---|---|---|---|
| 绿 `green` | 放心归位 / 可清 | 扩展名与名字规则命中的移动、你自己的标签分组、敏感命名隔离、配对与重复组里那条保留用的移动、可再生构建产物的废纸篓与永久删除 | 可勾选执行（含废纸篓；永久删除仍要 `--allow-permanent-delete`） |
| 黄 `yellow` | 你看一眼 | 待判断的移动（未知扩展名、顶层目录、派生副本，也就是 `reroutable` 为 true 的那些）、配对与重复组的处置候选、冷存候选的废纸篓与永久删除 | 只给「在访达或资源管理器里打开」与「移到废纸篓（可逆）」 |
| 红 `red` | 别动 | 全部 hold：禁刀区、被进程占用、被别处引用、静置未满、常驻白名单 | 只展示原因，最多给「打开所在位置」 |

判定就三行，没有例外：

```
kind == "hold"                      -> red
kind == "move"                      -> reroutable 为 true 是 yellow，否则 green
kind in ("trash", "delete")         -> tier 是 regenerable 才 green，其余 yellow
```

几处容易问的地方：

- **敏感命名的移动是绿的。** 隔离本身是最保守的动作，它把东西挪进一个单独的分区，
  没有读过内容，也没有删过任何东西。不动它反而更危险。
- **配对和重复组里，那条保留用的移动是绿的，旁边的处置候选是黄的。** 移动谁都不会丢，
  处置才需要你选。
- **冷存候选永远是黄的。** 大文件和用完的安装包看着像该清，但只有你知道那份 20GB
  的素材是不是明天还要用。
- **可再生产物是绿的，因为它能重新生成。** 这是唯一一类删了不心疼的东西，
  理由写在每条动作的 `restore_method` 里（重新跑一次构建就有）。
- **红的永远不可批准。** `approvable` 一定是 false，执行器见到红色的 id 出现在批准名单里直接抛错。

## 组：`group.color`

每个 group 恒为黄。组是一道选择题，不管你选哪个选项，都会有东西被处置掉，
这正是需要人看一眼的定义。组里各条 action 的颜色照上面那张表单独算，不受组的颜色影响。

## 目录层：`plan.mess`

```json
"mess": {
  "score": 59,
  "color": "yellow",
  "color_source": "rule",
  "counts": {"loose": 12, "aging": 1, "pending": 2, "groups": 3, "top_dirs": 3},
  "reason": {"zh": "...", "en": "..."}
}
```

五个数分别是：

| 键 | 数的是 |
|---|---|
| `loose` | 扫到的顶层散件总数（文件加目录），也就是 `summary.entries` |
| `aging` | 静置未满、正在等的条目数 |
| `pending` | 待判断的条目数，按 subject 去重（同一个文件有两条候选只算一个） |
| `groups` | 配对、重复、可再生三类组加起来的数量 |
| `top_dirs` | 顶层目录数，也就是 `summary.dirs` |

### 阈值

```
loose <= 3  且 pending <= 0   -> green
loose <= 15 或 pending <= 5   -> yellow
其余                          -> red
```

读法是：几件东西且没什么要你判断的，就是清爽；要么量还不大，要么要判断的不多，
就是有点乱；两条都不满足才是真的该收拾了。

阈值写在 `planner.MESS_THRESHOLDS`，这份文档是它的人话版本。改阈值要两边一起改，
`tests/test_cfo_colors.py` 里有一条测试专门盯着这件事。

### 分数

```
load     = max(loose/15, pending/5)
extra    = aging/20 + groups/12 + max(0, top_dirs - 5)/20
pressure = load + extra
score    = round(100 * pressure / (pressure + 1))
```

两个地方值得说一句。

`loose` 和 `pending` 取 max 不是相加，因为它们量的是同一堆东西的两个侧面，
加起来等于把同一堆数了两遍。

最后那一步 `p / (p + 1)` 是让分数逼近 100 但永远到不了。直接算加权和再截断的话，
一个只是有点乱的目录很容易就顶到 100，真正泥石流的那个目录就没地方可去了；
而且顶满之后你清掉三十个文件条也不动，看起来像坏了。用这条曲线，
27 件散件 3 件待判断的目录落在 69，四百件的落在 97，中间一直有得动。

几个参考点：空目录 0，三件散件 17，刚好压在黄线上（15 件或 5 件待判断）是 50。

分数只决定进度条有多长，不决定颜色；颜色只看上面的阈值，不看分数。
两者故意分开算，所以会出现分数不低但颜色还是黄的情况（两百个散件、
一个待判断项，分数 93 颜色黄），那不是 bug，那是在说「东西多，
但没什么要你拿主意的」。

### Agent 可以改目录颜色

阈值是对着数字猜的，Agent 是真看过这个目录的。所以 notes.json 里可以覆盖：

```json
{"mess": {"color": "red", "line": "数字上只是有点乱，但里面两个目录是三年前的项目，早该归档了"}}
```

覆盖之后 `mess.color` 变成 notes 给的值，`mess.color_source` 变成 `notes`，
规则原本的答案留在 `mess.rule_color`，谁都不用猜是谁改的。

**条目的颜色不能被 notes 覆盖，一个字都不行。** 目录颜色影响的是你要不要花时间，
条目颜色影响的是页面给不给你按钮，后者是安全边界，不能由一段文本决定。
